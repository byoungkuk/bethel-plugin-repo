# wiki-audit

구축된 LLM 위키의 정합성과 신선도를 점검하고 조치하는 유지보수 워크플로우입니다. wiki-ingest가 위키를 쌓고 wiki-activate가 읽어 쓰는 동안, 이 스킬은 위키가 단일 소스로서 신뢰를 유지하는지 점검합니다. 페이지가 누적될수록 중복·충돌·노후가 쌓이고, 이를 방치하면 활용 단계의 L1 검증이 흔들립니다.

## 전제 조건

1. 위키 폴더에 페이지가 1장 이상 존재합니다. 없으면 진행하지 않고 wiki-ingest로 먼저 인제스트할지 확인합니다.
2. 점검 범위(전체 / 특정 폴더 / 특정 페이지군)를 확인합니다.
3. 운영 지침(CLAUDE.md)이 없는 폴더는 스킬 기본값(`type`·MOC)으로 판정하면 오탐이 나기 쉬우므로, 폴더 기준(스키마·인덱싱)을 먼저 확인합니다(폴더 가드).

## 위키 폴더 지침 우선

위키 폴더에 운영 지침(CLAUDE.md 등)이 있으면 그 스키마·인덱싱·소스 표기 규약을 이 스킬 기본값보다 우선 적용합니다.

- 스키마: 폴더가 `type` 필드를 쓰지 않고 다른 분류 필드(예: `category`)로 개념/경험을 구분하면 그 필드를 따릅니다. 이때 `type` 미사용은 결함이 아닙니다.
- 인덱싱: 폴더가 MOC 대신 dataview index(예: index.md 자동수집)를 쓰면 수동 MOC 갱신·점검을 생략하고 index 노출만 확인합니다.
- 소스 표기: 폴더가 정한 sources 형식을 따릅니다. 위키링크(`[[ ]]`)는 노트형 소스에만 쓰고, docx·pptx·pdf 등 비노트 원본은 경로 문자열로 표기합니다.
- 명명·배치·본문 구조: 폴더가 파일명 접두어(예: `W_`)·하위 폴더(예: `wiki/`)·본문 섹션 구성(예: 8섹션)을 정하면 기본 템플릿보다 그 규약을 따릅니다.

폴더 지침이 없을 때만 아래 기본 규약(`type`·MOC)을 적용합니다.

## 점검 5군

| 군 | 점검 대상 | 대표 신호 |
|----|----------|----------|
| 중복 | 같은 주제 페이지 2장 이상 | 제목 유사, 내용 70% 이상 겹침 |
| 충돌 | 같은 사실에 다른 내용·수치 | 페이지마다 수치·정의 불일치 |
| 신선도 | 노후·소스 미반영 | updated 경과, sources 갱신 후 페이지 미수정 |
| 구조 | 링크·MOC·고아 | 깨진 [[ ]], MOC 미등록, 어디서도 링크되지 않은 고아 페이지 |
| 스키마 | frontmatter·유형 | 필수 필드 누락, concept·experience 혼합 |

각 군의 판정 기준은 `references/audit-checks.md`를 참조합니다.

## 프로세스 (Phase 0 ~ 5)

### Phase 0 — 위키 폴더 확인·점검 범위 설정

위키 폴더와 MOC 파일 위치를 확인합니다. 점검 범위를 정합니다. 소스 폴더는 신선도 비교(소스 갱신 대비 페이지 미반영) 점검에만 읽고, 이 스킬은 소스 폴더를 수정하지 않습니다.

### Phase 1 — 점검 모드 확정

| 모드 | 신호 | 범위 |
|------|------|------|
| 전체 감사 | 위키 점검, 헬스체크 | 위키 전체 5군 |
| 부분 감사 | 신선도만, 링크만, 중복만 | 지정 군만 |
| 인계 점검 | wiki-ingest에서 넘어온 충돌·중복 | 해당 페이지군 병합 판단 |

### Phase 2 — 위키 스캔·메타 수집

위키 페이지를 스캔해 메타를 모읍니다. 제목·type·sources·updated, [[ ]] 링크 목록, MOC 등록 여부, 본문 길이. 신선도 점검 시 sources 경로의 소스 노트 갱신 시각과 페이지 updated를 대조합니다.

### Phase 3 — 점검 실행 (Generator)

점검 5군을 관찰형 서술로 실행합니다. 판단·조치를 섞지 않고 발견 사실만 기록합니다. 예: "‘MCP’ 페이지와 ‘Model Context Protocol’ 페이지가 제목·정의에서 겹친다" — 병합 권고는 다음 단계에서 합니다.

관찰형 서술이 핵심입니다. 이 단계에서 곧장 병합·삭제를 결정하지 않습니다.

### Phase 4 — 평가·우선순위 (Evaluator)

Phase 3과 분리된 시점에서 발견을 평가합니다.

- 심각도 판정: 활용(L1 검증)에 영향을 주는 충돌·노후를 상위로, 링크 누락·고아를 하위로.
- 조치 유형 매칭: 각 발견에 병합·분할·갱신·링크 보정·삭제 후보 중 하나를 제안.
- 파괴적 조치 표시: 병합·삭제는 승인 필요 항목으로 별도 표시.

조치 유형 정의와 절차는 `references/audit-actions.md`를 참조합니다.

### Phase 5 — 리포트와 승인 후 조치

점검 리포트를 제시합니다. 리포트 형식은 `references/audit-actions.md`를 따릅니다.

- 비파괴 조치(링크 추가, MOC 등록, frontmatter 보정, updated 갱신): 사용자 동의 후 위키 폴더에 반영합니다.
- 파괴 조치(페이지 병합, 삭제): 자동 수행하지 않습니다. 대상·근거·병합 방향을 제시하고, 명시 승인을 받은 항목만 처리합니다.
- 충돌 페이지의 사실·수치 불일치: 어느 쪽이 맞는지 위키 안에서 단정하지 않습니다. 소스 노트 대조가 필요하면 근거 소스를 표시하고, 소스에 근거가 없으면 보충 리서치를 권합니다(위키 원천 품질이 필요하면 wiki-research, 일반 주제는 research-topic·book-research).

## 파괴적 작업 안전장치

- 병합·삭제·페이지명 변경은 승인 필수입니다. 승인 없이 실행하지 않습니다.
- 병합 시 양쪽 페이지의 sources·경험 기록을 손실 없이 합칩니다. 경험 페이지는 개념 페이지에 흡수하지 않고 유형을 유지합니다.
- 삭제 전 해당 페이지를 가리키는 [[ ]] 링크를 먼저 점검하고, 링크가 있으면 사용자에게 보고합니다.
- 조치 결과를 작업 끝에 변경 목록으로 표기합니다.

## Harness Engineering

- 생성-평가 분리: Phase 3(관찰)과 Phase 4(평가·우선순위)를 분리해, 발견과 조치 결정을 다른 시점에서 다룹니다.
- AI 흔적 제거: 리포트와 갱신 페이지에서 금지어(혁신적인·획기적인·완벽한·매우·쉽게·빠르게·~할 수 있습니다)와 모호한 수식을 제거합니다. 종결어미는 ~합니다체로 통일합니다.
- 보존 레벨:
  - L1 (원문 보존) — 페이지의 사실·수치·출처. 충돌 판정 시에도 임의로 고쳐 쓰지 않습니다.
  - L2 (재배열 허용) — 페이지 병합·분할·순서·링크 구조.
  - L3 (자유 생성) — 리포트 서술, 갱신 페이지의 연결 메모.
- 분량 가드레일: 리포트는 발견 위주로 압축합니다. 페이지 전문을 리포트에 복사하지 않고 위치와 핵심만 표기합니다.

## 출력 규약

- 한국어로 출력합니다. 날짜·시각은 KST 기준입니다. 신선도 임계값은 KST 현재 기준으로 계산합니다.
- 코워크(Cowork) 지시문·코드·설정은 코드 블록(```)에 넣습니다.
- 점검 리포트는 표로 정리합니다. 조치 후에는 변경 목록을 표기합니다.
- 위키 안에서 판정할 수 없는 충돌은 단정하지 않고 "소스 대조 필요"로 표시합니다.

## 참조 파일

- `references/audit-actions.md` — 조치 유형 정의(병합·분할·갱신·링크 보정·삭제), 절차, 리포트 형식, 코워크 지시문 예시.
