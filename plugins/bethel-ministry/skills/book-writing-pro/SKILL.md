# 책쓰기 전문 워크플로우 (Book Writing Pro Workflow) v1.0

7단계 구조적 집필 프로세스. 기본 책쓰기 워크플로우에 **작가 관점 선언**과 **경험·사례 주입** 단계를 추가한 전문 버전이다. 각 단계는 독립적 .docx 산출물을 생성한다.

## 전체 흐름

```
Phase 1: 기획 → Phase 2: 목차설계 → Phase 3: 챕터별 집필 → Phase 4: 경험·사례 주입 → Phase 5: 원고 통합 점검 → Phase 6: 퇴고 → Phase 7: 최종편집
```

사용자의 현재 상태를 파악해 적절한 단계부터 시작한다.
- 주제만 있음 → Phase 1부터
- 목차/아웃라인 업로드 → Phase 2 또는 3부터
- 기존 원고 업로드 → Phase 6부터

> **참조:** `hongstyle2.md`
> 챕터 작성 전 반드시 이 파일을 읽는다. 어조, 서술 시점, 문체 리듬, 어휘, 논리 전개, 핵심 규칙 5가지, 이탈 징후를 포함한다.

**이탈 징후 점검 시점:** 챕터 초안 완성 직후 `hongstyle2.md`의 이탈 징후 3개 항목으로 자가 점검한다. 하나라도 해당하면 해당 문단/소제목을 재작성한다. 퇴고 Phase 6 Pass 1에서도 동일 항목을 구조 편집 체크리스트에 포함하여 재점검한다.

## 공통 집필 원칙

> **참조:** `writing-principles.md`
> 문체, 금지어(①~⑦), 단어 선택, 분량 통제, AI 초안 규칙, AI 도구 표기의 상세 규칙을 포함한다. 모든 Phase에서 적용한다.

이하는 `writing-principles.md`에 없는 이 스킬 고유 규칙이다. 충돌 시 아래가 우선한다.

### 문단 기준 조정
- 문단은 **2~4문장**을 기본으로 한다 (`writing-principles.md`의 3~5문장 기준을 이 스킬에서 조정). 최대 5문장은 논리 전개가 필요한 경우에만 허용한다

### 문장 품질 기준 (GOOD/BAD 예시)

규칙보다 예시가 출력 품질에 더 큰 영향을 준다. 초안 작성 시 아래 쌍을 기준으로 삼는다.

| BAD (금지) | GOOD (기준) |
|-----------|------------|
| AI를 활용하면 쉽게 콘텐츠를 만들 수 있습니다 | AI에 원고 구조를 입력하면, 초안 생성 시간이 3시간에서 40분으로 줄어든다 |
| 혁신적인 방법으로 업무 효율을 높일 수 있습니다 | 반복 보고서 3건을 템플릿화하자, 주간 작성 시간이 절반이 됐다 |
| 이 기능은 매우 강력해서 다양한 작업에 활용할 수 있습니다 | 이 기능은 프롬프트 1개로 3가지 변형을 동시에 생성한다. 용도별로 골라 쓰면 된다 |

### 독자 프로필 적용 규칙

독자 정의는 Phase 1에서 수집하며, 수집된 독자 프로필을 전 단계에 걸쳐 적용한다. 프로젝트별 독자 프로필이 별도 파일로 존재하면 이를 참조한다.

**독자 유형별 서술 원칙:**
- **입문자**: "언제 이 기능/개념을 써야 하는가?"에 답하는 구조. 판단 기준과 반복 가능한 구조를 제공한다.
- **실무자**: 기준 → 적용 → 결과 해석 순으로 실습 예시 제시. 용도별 설계 기준과 품질 통제 방법을 제공한다.
- **기획자/강사**: 판단 기준을 문장으로 명확히 남겨 응용 가능하게. 효율적인 워크플로우와 재사용 구조를 제공한다.

### `[TODO]` 마커 유형 분류

집필 중 확인/보완이 필요한 구간에는 유형별 TODO 마커를 삽입한다. 퇴고 시 유형별로 필터링하여 우선순위를 판단한다.

| 마커 | 용도 | 예시 |
|------|------|------|
| `[TODO-FACT: ...]` | 수치·사실관계 확인 필요 | `[TODO-FACT: 해상도 기본값 확인]` |
| `[TODO-IMAGE: ...]` | 이미지·스크린샷 추가 필요 | `[TODO-IMAGE: 설정 화면 캡처 삽입]` |
| `[TODO-LINK: ...]` | 이전/이후 장 참조 확인 | `[TODO-LINK: Ch5 프롬프트 구조 참조 정확성 확인]` |
| `[TODO-EXAMPLE: ...]` | 예시·사례 보강 필요 | `[TODO-EXAMPLE: 실패 사례 추가]` |
| `[TODO-REVIEW: ...]` | 저자 판단·검토 필요 | `[TODO-REVIEW: 이 설명이 입문자에게 충분한지 확인]` |
| `[TODO-EXP: ...]` | 경험·사례 삽입 필요 | `[TODO-EXP: 이 소제목에 직접 경험 추가 필요]` |

## Phase 1: 기획 (Planning)

사용자에게 다음 정보를 수집한다:

1. **장르·형식**: 실용서/가이드북/교재/에세이/소설 등, 예상 분량
2. **핵심 주제**: 전제(premise), 핵심 질문, 또는 해결하려는 문제
3. **독자 정의**: 누구를 위한 책인지, 독자의 현재 수준과 기대 수준
4. **차별점**: 기존 유사서 대비 이 책만의 관점·구조·접근법
5. **종결어미**: ~다체 또는 ~합니다체. 장르·형식에 따라 추천하되 사용자가 최종 결정한다. 미지정 시 ~합니다체를 기본값으로 적용한다. 선택 기준은 `writing-principles.md`의 종결어미 선택 기준 표를 참조한다

### 작가 관점 선언 (Book Perspective)

Phase 1에서 기획 정보 수집과 함께, **이 책에서 작가가 말하고 싶은 것**을 구조화한다. 이 관점 선언이 이후 전 단계의 톤·방향·판단 기준을 결정한다.

> **참조:** `book-perspective-template.md`
> 이 템플릿을 기반으로 사용자와 대화하며 관점을 구체화한다.

수집 항목:

| 항목 | 질문 | 용도 |
|------|------|------|
| 핵심 주장 | "이 책을 한 문장으로 말하면?" | 전 챕터 관통 메시지 |
| 차별 시각 | "기존 책들과 다른 나의 시각은?" | 소제목·논리 전개 방향 |
| 독자에게 남길 판단 기준 | "독자가 이 책을 읽고 스스로 판단할 수 있게 되는 것은?" | 챕터별 마무리 설계 |
| 반복 키워드·개념 | "이 책에서 자주 등장할 핵심 용어와 내 정의는?" | 용어 일관성, glossary |
| 판단 문장 비율 | "이 책의 성격에 맞는 판단:설명 비율은?" | 문체 톤 조절 |
| 쓰지 않을 것 | "이 책에서 의도적으로 배제하는 접근·표현·범위는?" | anti-patterns |
| 경험 vs 근거 구분 | "내 경험에서 온 주장과 외부 근거의 비중은?" | 서술 톤 구분 |

**처리 규칙:**
- 7개 항목을 한꺼번에 묻지 않는다. 대화 흐름에서 자연스럽게 수집한다.
- 핵심 주장, 차별 시각, 쓰지 않을 것 — 이 3개가 최소 필수 항목이다. 나머지는 집필 과정에서 보완 가능하다.
- 수집된 관점은 `book-perspective-{프로젝트명}.md`로 저장하여 이후 단계에서 참조한다.

### 산출물: `01-book-plan.docx`

다음 항목을 포함:
- **책 개요**: 가제, 장르, 독자층, 예상 분량, 차별점, **종결어미(~다체 또는 ~합니다체)**
- **핵심 전제/논지**: 1~2문단 요약
- **작가 관점 선언**: Phase 1에서 수집한 관점 구조화 (이후 전 단계에서 참조)
- **독자 프로필**: Phase 1에서 수집한 독자 정의를 구체화 (이후 전 단계에서 참조)
- **구조 방향**: 전체 흐름 개요 (이해 → 설계 → 실행 → 확장 등)
- **캐릭터 프로필** (소설): 이름, 역할, 아크, 핵심 특성
- **리서치 노트** (논픽션): 조사 필요 주제, 핵심 자료 목록
- **일정**: 집필 마일스톤 (사용자에게 마감일 확인)

### 산출물: `book-perspective-{프로젝트명}.md`

작가 관점 선언 파일. 다음 항목을 포함:
- 핵심 주장 (한 문장)
- 차별 시각
- 독자에게 남길 판단 기준
- 반복 키워드·개념 정의 (glossary)
- 판단 문장 비율 기준
- 쓰지 않을 것 (anti-patterns)
- 경험 vs 근거 구분 기준

구조 템플릿이 필요하면 `book-perspective-template.md`를 참고한다.

## Phase 2: 목차설계 (Structure Design)

Phase 1의 기획 문서와 **작가 관점 선언**을 기반으로 상세 목차를 설계한다.

### 목차 설계 원칙

- 장(Chapter) 구성은 **이해 → 설계 → 실행 → 확장** 흐름을 기본 골격으로 삼되, 장르에 따라 조정
- 각 장은 2~4개 소제목으로 구성
- **소제목은 기능명이 아닌 행동·판단 중심 문장으로 작성**
  - ❌ "레이어 기능" → ✅ "레이어로 구조를 분리하는 기준"
  - ❌ "색상 설정" → ✅ "색상 선택이 결과에 미치는 영향을 판단하는 법"
- 각 장 말미에 반드시 **실무 정리 블록** 포함 계획:
  - 적용 체크리스트
  - 자주 발생하는 실수
  - 구조 예시 (프롬프트, 워크플로우 등)
- **작가 관점 선언의 핵심 주장이 목차 전체를 관통하는지 확인한다.** 핵심 주장과 무관한 챕터가 있으면 삭제하거나 연결 논리를 보강한다.

### 경험·사례 뱅크 초기 구성

목차 설계와 동시에, 챕터별로 삽입 가능한 경험·사례를 미리 수집한다.

> **참조:** `experience-bank-template.md`
> 이 템플릿을 기반으로 챕터별 경험 메모를 정리한다.

사용자에게 각 챕터에 대해 다음을 질문한다 (강제하지 않고, 떠오르는 것만 수집):
- "이 주제와 관련된 직접 경험이 있는가?"
- "수강생이나 클라이언트에게서 본 사례가 있는가?"
- "이 주제에서 실패한 경험이 있는가?"
- "생각이 바뀐 계기가 있는가?"

수집된 내용은 `experience-bank-{프로젝트명}.md`에 정리한다. Phase 3에서 초안 작성 시 참조하고, Phase 4에서 추가 삽입한다.

### 프로젝트별 확정 목차 참조

프로젝트별 확정 목차가 별도 파일(예: `references/project-toc.md`)로 존재하면 이를 참조한다. 챕터 작성 시 전체 구조 안에서의 위치, 앞뒤 챕터와의 연결, 파트별 톤을 반드시 확인한다.

### 산출물: `02-table-of-contents.docx`

다음 항목을 포함:
- **전체 목차**: Part → Chapter → 소제목 계층 구조
- **챕터별 시놉시스**: 각 챕터 2~3문장 요약 (목적, 핵심 내용, 독자가 얻는 것)
- **챕터별 예상 분량**: 글자 수 범위
- **챕터 간 연결 논리**: 앞 챕터에서 다음 챕터로 이어지는 흐름 설명

### 산출물: `experience-bank-{프로젝트명}.md`

챕터별 경험·사례 뱅크 초안. Phase 3~4에서 지속 업데이트.

## Phase 3: 챕터별 집필 (Chapter Drafting)

Phase 2의 목차를 청사진으로 사용한다. 사용자가 기존 아웃라인을 업로드한 경우 그것을 기반으로 한다.

### 집필 전 참조 파일

챕터 작성 전 반드시 다음 파일을 확인한다 (우선순위 순):
1. **홍작가 문체 가이드** (`hongstyle2.md`) — 어조, 리듬, 핵심 규칙, 이탈 징후
2. **작가 관점 선언** (`book-perspective-{프로젝트명}.md`) — 핵심 주장, 차별 시각, 쓰지 않을 것
3. **경험·사례 뱅크** (`experience-bank-{프로젝트명}.md`) — 해당 챕터에 배정된 사례
4. **챕터 템플릿** (프로젝트별 별도 파일이 있으면 참조)

그 외 파일(glossary, anti-patterns, writing-principles)은 필요 시에만 참조한다.

### 컨텍스트 리셋 규칙

**매 챕터 진입 시 아래 3개 항목을 반드시 재확인한다.** 같은 대화에서 이전 챕터를 이미 작성했더라도, 새 챕터 시작 전에 다시 확인한다. 긴 대화에서 앞쪽 규칙이 희석되는 것을 방지하는 장치다.

1. **종결어미** — Phase 1에서 결정된 종결어미(~다체 또는 ~합니다체) 재확인
2. **작가 관점** — 이 챕터에서 적용할 핵심 주장·차별 시각 재확인
3. **독자 프로필** — 독자 수준과 이 챕터에서의 난이도 위치 재확인

3챕터 연속 작성 후에는 금지어 규칙(①~⑥)도 재확인한다.

### 챕터 출력 슬롯 템플릿 (초안은 반드시 이 구조를 따른다)

챕터 초안은 아래 슬롯을 순서대로 채운다. 슬롯을 건너뛰거나 순서를 바꾸지 않는다.

```
[도입] ← "왜 이 단계/주제가 필요한가" (1~2문단)
[소제목 1] ← 개념 또는 판단 기준 제시
  [기준] ← 핵심 판단 기준 1문장
  [근거/사례] ← 기준을 뒷받침하는 설명·경험
[소제목 2~N] ← 동일 구조 반복
[실무 정리 블록] ← 체크리스트 / 자주 하는 실수 / 구조 예시
[연결] ← 다음 장으로의 전환 문장
```

소제목 안의 내용은 자유롭게 작성하되, **[기준] → [근거/사례] 순서는 역전하지 않는다.** 근거나 방법부터 시작하면 "그래서 뭘 하면 되지?"만 남는 글이 된다.

### 집필 규칙

- **챕터 단위로 작성**, 각각 별도 `.docx` 파일로 저장
- 각 챕터 시작 시 내부 메모 포함: 챕터 목표, 핵심 포인트, 목표 분량, **이 챕터에서 적용할 작가 관점**
- 일관된 문체, 시제, 서술 시점 유지
- 확인/보완 필요 구간은 유형별 `[TODO-유형: ...]` 마커 삽입 (공통 집필 원칙의 TODO 마커 유형 분류 참조)
- 경험·사례 뱅크에 해당 챕터 사례가 있으면 초안에 반영한다. 없으면 `[TODO-EXP: ...]` 마커를 삽입한다
- 실용서 기본 분량: 챕터당 3,000~6,000자 (사용자 지정 가능)

### 장 작성 요청 템플릿

사용자가 챕터 작성을 요청할 때, 다음 항목을 확인한다. 사용자가 템플릿 형식으로 제공하지 않더라도, 메시지에서 해당 정보를 추출하여 적용한다.

```
[장 작성 요청]
■ 장 번호/제목:
■ 참조 자료: (첨부 또는 링크)
■ 이전 장 원고: (첨부 또는 "프로젝트 지식 참조")
■ 핵심 판단 기준: 이 장에서 가장 강조할 기준은?
■ 독자 잔상: 독자가 이 장을 읽고 남겨야 할 것은?
■ 작가 메모: 이 챕터에서 꼭 넣고 싶은 생각·경험·관점은?
■ 분량 지정: (예: 소제목당 2문단 / 미지정 시 기본값 적용)
```

**처리 규칙:**
- 7개 항목 중 하나라도 빠지면, **빠진 항목만** 사용자에게 질문한다 (전체 템플릿을 다시 요청하지 않는다)
- 모든 항목이 확인되면 바로 초안을 작성한다
- "핵심 판단 기준", "독자 잔상", "작가 메모" 3개가 초안 방향을 결정하는 핵심 항목이다. 이 3개가 빠진 채로 초안을 시작하지 않는다. **추측으로 채우지 않고 사용자에게 질문한다.**

### 원문 보존 강도 레벨

사용자의 요청 동사에 따라 보존 강도를 자동 판별한다. 레벨을 혼동하지 않는다.

| 레벨 | 트리거 | 허용 범위 | 금지 행위 |
|------|--------|----------|----------|
| **L1 교정** | "다듬어줘", "교정해줘", "수정해줘" | 맞춤법·띄어쓰기·종결어미 통일만. 문장 구조 변경 금지 | 문장 분리·병합, 새 문장 추가, 문단 재배치 |
| **L2 정리** | "정리해줘", "깔끔하게", "보강해줘" | 문장 분리·접속 보강, 지정 부분 내용 추가. 미지정 부분 원본 유지 | 구조 재배치, 슬롯 순서 변경, 미지정 부분 수정 |
| **L3 리라이팅** | "리라이팅해줘", "다시 써줘" | 구조 재배치·문장 교체·패턴 적용 허용 | 분량 120% 초과 (초과 시 사유 확인) |

- 사용자가 레벨을 명시하지 않으면 트리거 동사로 자동 판별한다
- 초안 작성 시 사용자가 분량을 지정하지 않으면, 소제목당 2~3문단을 기본값으로 한다

### 챕터 집필 프로세스

1. 목차에서 해당 챕터 시놉시스 확인
2. **작가 관점 선언에서 이 챕터에 해당하는 관점 확인**
3. **경험·사례 뱅크에서 이 챕터에 배정된 사례 확인**
4. **첫 문장: "왜 이 단계/주제가 필요한가"로 시작** (기능 소개 시작 금지)
5. 개념 → 판단 기준 → 실제 적용 방식 순서로 본문 전개
6. 경험 뱅크의 사례를 본문 논리 흐름에 자연스럽게 배치
7. 문단은 2~4문장 이내 유지 (최대 5문장)
8. 챕터 끝: 다음 장으로의 연결 문장 + 실무 정리 블록
9. 유형별 `[TODO-유형: ...]` 마커 삽입 (리서치/검토/경험 필요 부분)
10. **초안 자가 점검 (출력 전 반드시 실행)**: 초안 완성 직후 아래 전체 항목 확인. 해당 항목이 있으면 해당 문장을 수정한 뒤 출력한다.

    **이탈 징후 점검:**
    - [ ] 방법·팁·요령이 기준 설명 없이 먼저 등장하는가?
    - [ ] 감정적 공감이나 동기 부여 문장이 논리 설명보다 앞서는가?
    - [ ] 글을 읽고 난 뒤 기준 변화 없이 "그래서 뭘 하면 되지?"만 남는가?

    **금지어·문체 점검:**
    - [ ] "혁신적인", "획기적인", "완벽한" 등 과장형 형용사 포함 여부
    - [ ] "~할 수 있습니다" 추측 표현 포함 여부
    - [ ] "매우", "쉽게", "빠르게" 등 모호한 부사 포함 여부
    - [ ] 추상 명사 중심 문장 포함 여부

    **슬롯 구조 점검:**
    - [ ] [기준] → [근거/사례] 순서가 지켜졌는가?
    - [ ] [실무 정리 블록]이 누락되지 않았는가?

    → 하나라도 해당하면 해당 문단/소제목을 재작성한다
11. `chapter-XX-draft.docx`로 저장

### 실무 정리 블록 구성

각 챕터 말미에 다음 중 적합한 항목을 포함:
- **적용 체크리스트**: 이 챕터에서 배운 내용을 실무에 적용할 때의 점검 항목
- **자주 발생하는 실수**: 독자가 흔히 빠지는 함정과 대처법
- **구조 예시**: 프롬프트, 워크플로우, 판단 흐름도 등

### 형식 및 가독성

- 번호 목록, 단계 박스, 비교 표 적극 활용
- 텍스트가 주가 되며, 이미지는 설명 보조 역할
- 모든 이미지/예시에는 **"왜 이것을 예시로 썼는지"** 설명 필수
- 이미지 캡션: 감상평 금지, 기능·의도·판단 기준 중심

### 장 간 일관성·반복 방지

다수 챕터에 걸쳐 용어, 개념 설명, 난이도가 흔들리지 않도록 다음 규칙을 적용한다.

**용어 일관성:**
- 동일 개념에 대해 장마다 다른 용어를 사용하지 않는다 (예: "프롬프트 구조"와 "명령어 체계"를 혼용하지 않음)
- 새 용어가 등장하면 최초 1회 정의하고, 이후 장에서는 정의 없이 사용한다
- 용어 정의가 필요할 때는 이전 장에서 사용한 표현을 그대로 따른다
- **작가 관점 선언의 glossary(반복 키워드·개념 정의)를 기준으로 한다**

**반복 방지:**
- 챕터 작성 전, 이전 장에서 이미 설명한 개념인지 확인한다
- 이미 설명한 개념을 다시 다뤄야 할 경우: 재설명하지 않고 **"N장에서 다룬 [개념명]을 기준으로"** 형태로 참조한다
- 같은 파트(Part) 내에서 동일한 판단 기준이나 원칙을 두 번 이상 풀어 설명하지 않는다

**난이도 관리:**
- 파트 순서에 따라 난이도가 자연스럽게 상승한다. 뒤 파트에서 앞 파트 수준의 기초 설명을 반복하지 않는다
- 파트 내 첫 장은 해당 파트의 핵심 개념을 도입하고, 이후 장들은 이를 전제로 전개한다

### Phase 3 → Phase 4 전환 규칙

전 챕터를 모두 완성한 뒤 Phase 4로 넘어가는 것이 기본이지만, **파트(Part) 단위 순환도 허용한다.**

**전환 모드:**

| 모드 | 흐름 | 적합한 경우 |
|------|------|------------|
| 일괄 전환 | 전 챕터 Phase 3 완료 → 전 챕터 Phase 4 | 챕터 수 10개 이하, 경험 뱅크가 미리 정리된 경우 |
| 파트 단위 순환 | Part A Phase 3 → Part A Phase 4 → Part B Phase 3 → Part B Phase 4 → ... | 챕터 수 12개 이상, 앞 파트 경험 삽입 결과가 뒤 파트 집필에 영향을 줄 때 |

- 사용자가 모드를 지정하지 않으면 **일괄 전환**을 기본값으로 한다.
- 파트 단위 순환 시, Phase 5(통합점검)는 **모든 파트의 Phase 4가 끝난 후** 1회만 실행한다.
- 어떤 모드든, Phase 4 진입 전 해당 챕터의 초안이 이탈 징후 자가 점검을 통과한 상태여야 한다.

## Phase 4: 경험·사례 주입 (Experience Injection)

Phase 3의 초안이 완성된 후, 각 챕터에 작가의 경험·사례를 삽입하는 단계. **논리 골격 위에 경험을 얹어, 경험이 "증거"로 작동하게 만드는 것**이 이 단계의 목적이다.

### 왜 Phase 3 이후인가

Phase 3의 초안은 논리 골격이다. 개념 → 판단 기준 → 적용 방식이 잡혀 있는 상태. 이 골격 위에 경험을 얹어야 경험이 논증의 도구로 기능한다. 골격 없이 경험부터 쓰면 수필이 되고, 경험 없이 퇴고에 들어가면 "맞는 말인데 와닿지 않는 글"이 된다.

### 작업 흐름

```
초안 읽기 → [TODO-EXP] 마커 확인 → 작가 경험 입력 → 본문 녹여쓰기 → 경험 로그 기록
```

### 경험 주입 입력 템플릿

사용자가 챕터별로 다음을 입력한다. 한 챕터에 여러 사례를 넣을 수 있다.

```
[경험 주입 요청]
■ 챕터: Ch[번호]
■ 삽입 위치: [소제목명] 뒤 / [문단 지정] / Claude 판단에 맡김
■ 유형: 직접경험 / 관찰사례 / 실패담 / 비교사례 / 전환점
■ 메모: (자유 형식 3~5줄)
■ 이 사례가 증명하는 판단 기준: (한 문장)
```

**유형 정의:**

| 유형 | 설명 | 서술 톤 |
|------|------|---------|
| 직접경험 | 내가 했던 일, 겪은 상황 | 1인칭, 구체적 시간·장소·행위 묘사 |
| 관찰사례 | 수강생, 클라이언트, 동료에게서 본 것 | 3인칭 관찰, 간접 인용 화법 |
| 실패담 | 시도했으나 안 된 것, 왜 안 됐는지 | 1인칭, 과정 서술 → 원인 진단 |
| 비교사례 | A 방식 vs B 방식을 해본 결과 | 대조 구조, 조건·결과 병렬 |
| 전환점 | 생각이 바뀐 계기 | 1인칭, 이전 관점 → 계기 → 이후 관점 |

### "Claude 판단에 맡김" 위치 선정 기준

삽입 위치를 사용자가 지정하지 않을 경우, 다음 기준으로 위치를 결정한다:

| 경험 유형 | 기본 배치 위치 | 이유 |
|-----------|--------------|------|
| 직접경험 | 판단 기준 제시 직후 | 기준의 실제 근거로 기능 |
| 관찰사례 | 문제 상황 제시 직후 (소제목 도입부) | 독자 공감 유도, "이런 경우를 봤다" |
| 실패담 | "왜 흔들리는가" 설명과 기준 재정의 사이 | 기존 방식의 한계를 체감시킴 |
| 비교사례 | 방법론 비교 또는 선택 기준 제시 구간 | 조건별 결과 차이를 보여줌 |
| 전환점 | 장 도입부 또는 관점 전환 마무리 | 사고 전환의 계기로 기능 |

- 한 소제목 안에 경험이 2개 이상 들어가면 논리 흐름이 끊긴다. **소제목당 경험 1개를 기본**으로 한다.
- 배치 후 앞뒤 문단과의 연결이 자연스러운지 반드시 확인한다.

### 처리 규칙

1. **경험은 별도 박스나 칼럼으로 분리하지 않는다.** 본문 논리 흐름 안에 녹인다
2. 경험 문단의 톤: 해당 유형의 서술 톤을 따르되, 반드시 판단 기준으로 귀결한다
3. 삽입 후 해당 소제목의 분량이 원본 대비 130%를 초과하면 작가에게 확인한다
4. 하나의 챕터에 경험 유형이 편중되지 않도록 유형 분포를 리포트한다
5. `[TODO-EXP]` 마커가 남아 있으면 작가에게 알린다 — 경험 없이 넘어갈지, 추가할지 확인
6. 경험 뱅크(`experience-bank-{프로젝트명}.md`)에 있으나 Phase 3 초안에 반영되지 않은 사례도 이 단계에서 삽입한다
7. 삽입된 경험은 홍작가 핵심 규칙 3번("사례는 결론을 증명하기 위한 도구로만 사용한다")을 따른다

### 경험 삽입 품질 체크

각 삽입된 경험에 대해 다음을 확인한다:

| # | 점검 항목 | 상태 |
|---|----------|------|
| 1 | 경험이 해당 소제목의 판단 기준을 뒷받침하는가 | ☐ |
| 2 | 경험이 본문 논리 흐름에 자연스럽게 연결되는가 (별도 블록처럼 보이지 않는가) | ☐ |
| 3 | 경험의 서술 톤이 유형에 맞는가 (1인칭/3인칭, 구체성 수준) | ☐ |
| 4 | 경험이 감정 표현이나 동기 부여로 빠지지 않고 판단 기준으로 귀결되는가 | ☐ |
| 5 | 동일 경험이 다른 챕터에서 중복 사용되지 않는가 | ☐ |

## Phase 5: 원고 통합 점검 (Manuscript Integration Review)

Phase 4(경험 주입) 완료 후, 단일 원고로 통합하기 전에 장 간 연결과 일관성을 점검한다. 이 단계를 거치지 않고 Phase 6으로 진입하지 않는다.

### 통합 점검 체크리스트

| # | 점검 항목 | 상태 |
|---|----------|------|
| 1 | 장 간 연결 문장이 자연스럽게 이어지는가 (앞 장 마무리 → 뒷 장 도입) | ☐ |
| 2 | 동일 용어가 전체 원고에서 일관되게 사용되는가 | ☐ |
| 3 | 파트별 난이도 곡선이 자연스럽게 상승하는가 | ☐ |
| 4 | 동일 개념이 서로 다른 장에서 중복 설명되는 곳은 없는가 | ☐ |
| 5 | Phase 1에서 결정된 종결어미(~다체 또는 ~합니다체)와 문체 톤이 전체적으로 통일되어 있는가 | ☐ |
| 6 | 앞 장 참조("N장에서 다룬...")가 실제 해당 장의 내용과 일치하는가 | ☐ |
| 7 | 실무 정리 블록의 형식·깊이가 챕터 간에 균형 잡혀 있는가 | ☐ |
| 8 | `[TODO]` 마커 현황 정리: 유형별 잔존 수량과 해결 계획 확인 | ☐ |
| 9 | **경험·사례 분포 점검**: `04-experience-log.md` 기준, 챕터별 경험 유형 편중 없는가 | ☐ |
| 10 | **경험·사례 중복 점검**: 동일 사례가 복수 챕터에서 반복되지 않는가 | ☐ |
| 11 | **경험 누락 점검**: 경험 뱅크에 있으나 어디에도 삽입되지 않은 사례가 있는가 | ☐ |
| 12 | **작가 관점 일관성**: 핵심 주장이 전 챕터를 관통하는가, 빗나간 챕터는 없는가 | ☐ |

### 통합 작업

점검 완료 후 단일 원고로 통합:
- 표지 페이지
- 목차
- 전체 챕터 순서대로
- 부록 (해당 시)

## Phase 6: 퇴고 (Revision & Editing)

### 역할 전환 선언 (퇴고 진입 조건)

이 단계에서는 집필자의 시점을 내려놓는다. 편집자로서, 집필 의도를 참고하지 않고 **독자 시점에서만 판단**한다. "왜 이렇게 썼는가"가 아니라 "독자가 읽었을 때 작동하는가"를 기준으로 점검한다. 이 선언 없이 체크리스트를 돌리면, 구조적 문제보다 표현만 다듬는 쪽으로 흐른다.

3회 패스 편집 체크리스트를 적용한다. 편집된 원고와 함께 체크리스트 리포트를 산출한다.

> **참조:** `editing-checklist.md`
> Pass 1(구조 편집 14항목), Pass 2(문장 편집 11항목 + 금지어 점검 6항목), Pass 3(교정 9항목)의 상세 체크리스트를 포함한다. Phase 6 진입 시 반드시 이 파일을 읽고 실행한다.

### 산출물

| 파일 | 설명 |
|------|------|
| `06-manuscript-edited.docx` | 퇴고 완료 원고 |
| `06-editing-report.docx` | 3회 패스 체크리스트 결과 + 주요 변경 사항 기록 |

## Phase 7: 최종편집 (Final Polish)

퇴고 완료 원고를 출판/배포 수준으로 마무리한다.

### 최종편집 항목

1. **서문(프롤로그)**: 책의 목적, 독자에게 하는 약속, 이 책의 활용법
2. **에필로그/맺음말**: 전체 여정 요약, 독자의 다음 단계 제시
3. **각 챕터 도입부 훅(hook) 점검**: 첫 문장이 왜 필요한가를 명확히 전달하는지 최종 확인
4. **부록 정리**: 참고 자료, 용어 사전, 추가 리소스
5. **표지·판권 페이지**: 가제 확정, 저자 정보
6. **전체 흐름 최종 검수**: 처음부터 끝까지 읽으며 독자 경험 점검
7. **작가 관점 최종 확인**: 핵심 주장이 서문~에필로그까지 일관되게 관통하는지 점검

### 산출물: `07-manuscript-final.docx`

최종 완성본. 다음을 포함:
- 표지 페이지
- 목차 (자동 생성)
- 서문
- 전체 챕터
- 에필로그
- 부록 (해당 시)
- 판권 페이지
