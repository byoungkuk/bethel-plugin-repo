# 블로그 글쓰기 워크플로우 (Blog Writing Workflow)

홍작가 블로그(sshong.com, WordPress)에 최적화된 5단계 글쓰기 프로세스. 브런치는 write-brunch, 페이스북은 write-facebook, 비블로그 채널은 write-content, 에세이는 write-essay, 장편(책)은 book-writing를 사용한다.

## 블로그 플랫폼 이해

스킬의 모든 단계는 아래 플랫폼 특성을 전제로 한다.

### SEO 검색 유입 기반 플랫폼

sshong.com은 WordPress 기반 블로그로, **검색 엔진 유입이 핵심 트래픽 경로**다. 브런치의 에디터 큐레이션과 달리, 구글·네이버 검색 결과에서 제목과 메타 설명이 클릭을 결정한다. 제목·소제목·본문에 검색 키워드가 자연스럽게 포함되어야 한다.

### 사이트 구조

- URL 형식: `sshong.com/blog/{post_id}`
- 주요 카테고리: 생성형AI/챗GPT, 글쓰기, 영상제작/AI영상, 일하는법/생산성, 책쓰기, 강의, 홍순성
- 태그 시스템: 글당 2~4개 태그 부여
- 대표 이미지(Featured Image): 모든 글에 필수
- TOC(목차): Contents 플러그인으로 H2/H3 기반 자동 생성

### 독자 행동 패턴

- 검색 → 제목+메타설명 확인 → 클릭 → TOC로 원하는 섹션 점프
- 글을 처음부터 끝까지 읽기보다, **소제목을 훑으며 필요한 부분만 읽는 독자** 비율이 높다
- 관련 글 링크를 따라 다음 글로 이동하는 패턴
- 읽기 시간: 3~7분 (1,200~2,500자)

### 홍작가 블로그 글의 특징

sshong.com 블로그 글은 다음 특성을 일관되게 유지한다.

**단락 구조 — 일반 문서 형식:**
한 문장을 독립 줄로 배치하는 모바일식 시적 배치는 사용하지 않는다. 문단은 2~5문장이 하나의 의미 단위를 이루는 일반 문서 형식을 따른다. 문장 간 줄바꿈은 단락이 완전히 바뀔 때만 사용한다. 강조·전환이 필요한 문장도 단락 내에 자연스럽게 배치한다.

**내부 링크 적극 활용:**
관련 글·시리즈 글·참고 자료를 본문 내에 자연스럽게 삽입한다. 링크는 문장 끝이나 섹션 끝에 `관련글 제목 ·` 형태로 배치한다.

**시리즈 번호 체계:**
같은 주제의 연속 글에는 원(①②③) 또는 괄호(⓪) 번호를 제목 앞에 붙인다. 단독 글에는 번호를 붙이지 않는다.

## 전체 흐름

```
Step 1: 주제·앵글 설계 → Step 2: 구조 설계 → Step 3: 초안 작성 → Step 4: 리라이팅 → Step 5: 발행 준비
```

사용자의 상태에 따라 적절한 단계부터 시작한다.
- 주제만 있음 → Step 1부터
- 앵글/구조 있음 → Step 3부터
- 초안 있음 → Step 4부터
- 다른 스킬에서 변환 (책 챕터 → 블로그 글 등) → Step 2부터

### Step 간 전환 규칙

각 Step 완료 후, 다음 Step으로 넘어가기 전에 사용자 확인을 받는다.

| 전환 | 확인 방식 |
|------|----------|
| Step 1 → 2 | 주제·앵글·독자·글 유형·카테고리를 요약 제시하고, 확정 여부를 확인한 뒤 구조 설계로 진행한다 |
| Step 2 → 3 | 아웃라인(H2/H3 소제목 포함)과 제목 후보를 제시하고, 구조 수정이 필요한지 확인한 뒤 초안 작성으로 진행한다 |
| Step 3 → 4 | 초안을 제시하고, 방향 수정이나 추가 요청이 있는지 확인한 뒤 리라이팅으로 진행한다 |
| Step 4 → 5 | 수정본을 제시하고, 추가 수정이 필요한지 확인한 뒤 발행 준비로 진행한다 |

사용자가 "끝까지 진행해줘" 또는 "한 번에 해줘"라고 요청한 경우, 확인 없이 연속 진행한다.

## 공통 집필 원칙

### 문체 기준

- 표준어 사용
- 종결어미는 **'~합니다'체 고정** (sshong.com 블로그의 기본 문체. 별도 지정 없으면 변경하지 않는다)
- 문장은 15~25단어 내외 기본 (블로그의 가독성과 정보 밀도 균형)
- **한 문장에는 하나의 정보, 하나의 판단만 담는다**
- 문장은 능동형을 기본으로 한다
- 문단은 2~5문장을 기본으로 한다
- **단락 형식:** 문단은 2~5문장이 하나의 의미 단위를 이루는 일반 문서 구조를 따른다. 문장별 단독 줄바꿈(모바일식 시적 배치)은 사용하지 않는다
- 감정적 표현, 감탄형 문장 지양
- 전체 톤은 차분하고 설명적인 문체 유지

### 블로그 톤 가이드

sshong.com 블로그 글은 **설명과 판단의 중간**에 위치한다. 정보만 나열하는 글도 아니고, 개인 감상만 담은 글도 아니다. 아래 유형별로 톤을 조정한다.

| 글 유형 | 톤 | 특징 |
|---------|-----|------|
| 방법론 해설 | 설계자 | 개념을 정의하고, 단계를 나누고, 각 단계의 판단 기준을 명시한다 |
| 도구·기능 리뷰 | 실험자 | 직접 사용한 경험 기반. 기능 나열이 아니라 어떤 기준으로 평가했는지를 중심에 둔다 |
| 인사이트·관점 | 분석적 관찰자 | 현상을 재정의하고, 기존 관점과 다른 기준을 제시한다 |
| 경험 기반 글 | 실무 기록자 | 강의·컨설팅·집필 현장에서 얻은 관찰과 판단을 정리한다 |
| 가이드·튜토리얼 | 구조적 안내자 | 조건 → 기준 → 결과 순서로 정리. 프롬프트·스크린샷 등 실행 가능한 재료 포함 |
| 출간·강의 안내 | 정보 전달자 | 핵심 내용, 대상, 구성을 간결하게 전달한다 |

### 서술 전략

- 글의 첫 문장: **현상 관찰, 독자의 문제 상황, 또는 판단의 선언**으로 시작. 정의나 개념 나열로 시작하지 않음
- 설명 순서: **상황 → 기준 → 적용 방식**
- 소제목(H2/H3)은 기능명이 아닌 **판단·행동 중심 문장**으로 작성
- "가능하다"보다 **"이렇게 판단한다"** 식의 단정적 서술
- 마무리는 요약이 아니라 **핵심 메시지 압축** 또는 **독자의 다음 행동 기준** 제시

### 글쓰기 금지어 규칙

모든 문장은 **판단·기준·결과**가 드러나야 한다.

**① 과장형 형용사 금지**
금지어: 혁신적인, 획기적인, 창의적인, 강력한, 완벽한, 최고의, 탁월한, 뛰어난
→ 무엇이 어떻게 다른지, 수치·사례로 설명한다.

**② 모호한 부사 금지**
금지어: 매우, 굉장히, 상당히, 꽤, 쉽게, 빠르게, 간편하게, 효율적으로
→ 시간·단계·수치·조건으로 대체한다.

**③ 추측·완곡 표현 금지**
금지어: ~할 수 있습니다, ~일 수 있습니다, ~라고 볼 수 있습니다, 어느 정도, 부분적으로, 다소
→ 단정형으로 서술한다. 조건이 있다면 조건을 먼저 제시한다.

**④ 불필요한 여유 연결어 금지**
금지어: 전반적으로 볼 때, 일반적으로 말하면, 어떤 면에서 보면, 이러한 측면에서, 결과적으로
→ 근거 → 주장 구조로 직접 연결한다.

**⑤ 추상 명사 중심 문장 지양**
주의어: 중요성, 필요성, 가능성, 효과, 가치, 측면, 부분
→ 동사 중심 문장으로 전환. 장면·행동·결과로 구체화한다.

**⑥ AI 흔적 조합 금지**
부사 + 형용사 + 가능성 표현 + 추상 명사 패턴은 금지한다.

### 금지 요소

- 정보 나열식 구성 (리스트만 던지고 해설 없는 글)
- 결과물에 대한 감상형 표현
- 과도한 반복 설명
- 근거 없는 과장·미사여구
- "오늘은 ~에 대해 이야기해 보겠습니다" 식의 메타 서술
- 검색 키워드를 부자연스럽게 반복 삽입하는 행위
- **"Written by 홍순성 on …" 형식의 작성자·날짜 표기** — 출력물에 포함하지 않는다
- **"Contents" 박스** — H2/H3 소제목을 불릿 리스트로 나열하는 TOC 박스는 출력물에 포함하지 않는다. TOC는 워드프레스 플러그인이 자동 생성한다
- **문장별 단독 줄바꿈(모바일식 시적 배치)** — 단락은 의미 단위로 묶어 일반 문서 형식으로 작성한다

### 홍작가 글쓰기 스타일

이 스킬의 모든 글은 아래 스타일 기준을 최우선으로 적용한다.

**한 문장 정의:** 현상을 관찰해 문제를 재정의하고, 해결이 아닌 기준의 이동을 통해 독자의 사고 방식을 정렬하는 설명 중심 글쓰기.

**어조:** 가르치지 않되 이끈다. 독자 위에 서지 않고 같은 문제를 함께 바라보는 위치를 취한다.

**문체 리듬:** 단문 중심, 필요 시 단문으로 리듬을 끊는다. 문단 초반은 관찰이나 상황 제시로 들어가고, 후반으로 갈수록 판단 밀도가 높아지는 점층 구조.

**논리 전개:** 현상 관찰 → 문제 지점 명확화 → 기준 재정의 → 관점 전환.

**핵심 규칙 5가지:**
1. 해결책을 서두르지 말고, 먼저 문제의 기준부터 다시 정의한다.
2. 기능·방법 설명보다, 왜 그 방식이 흔들리는지를 먼저 설명한다.
3. 사례는 결론을 증명하기 위한 도구로만 사용한다.
4. 독자의 행동을 바꾸려 하지 말고, 판단 기준을 이동시키는 데 집중한다.
5. 글의 마지막은 요약이 아니라 관점의 재정렬로 마무리한다.

## Step 1: 주제·앵글 설계 (Topic & Angle Design)

글을 쓰기 전에 다음 6가지를 명확히 한다.

### 수집 항목

| 항목 | 질문 | 예시 |
|------|------|------|
| **주제** | 무엇에 대해 쓰는가? | AI 글쓰기 워크플로우, 프롬프트 수정 설계, 건설안전 AI 활용 |
| **앵글** | 이 주제를 어떤 시선으로 보는가? 기존 관점과 무엇이 다른가? | "AI 글쓰기의 차이는 프롬프트가 아니라 수정 과정의 설계에서 발생한다" |
| **독자** | 누가 읽는가? 검색할 때 어떤 질문을 품고 있는가? | AI 글쓰기를 시작한 실무자, 프롬프트만으로는 한계를 느끼는 사용자 |
| **글 유형** | 어떤 형식인가? | 방법론 해설 / 도구 리뷰 / 인사이트 / 경험 기반 / 가이드 / 안내 |
| **카테고리** | sshong.com의 어떤 카테고리에 속하는가? | 생성형AI/챗GPT, 글쓰기, 책쓰기, 일하는법/생산성, 강의 등 |
| **시리즈** | 기존 시리즈에 포함되는가? 단독 글인가? | 시리즈명, 회차 번호 (선택) |

### 앵글 설계 기준

sshong.com 블로그에서 검색 유입과 재방문을 만드는 글은 정보 전달이 아니라 **판단 기준의 제시**에 있다. 앵글을 잡을 때 다음을 점검한다.

- **검색 의도와 맞닿는가** — 독자가 이 주제로 검색할 때 기대하는 답이 무엇인지 파악한다. 그 답을 주되, 기존 검색 결과와 다른 기준을 제시한다.
- **경험에서 나온 판단인가** — 직접 실험, 강의 현장, 집필 과정에서 얻은 기준이 포함되어야 한다.
- **구조화할 수 있는가** — 블로그 글은 소제목과 TOC로 구조화되어야 한다. 앵글이 2~4개의 소제목으로 나뉘는지 확인한다.

### SEO 키워드 설계

- 핵심 키워드 1개 + 보조 키워드 2~3개를 선정한다
- 핵심 키워드는 제목과 H2 소제목에 자연스럽게 포함한다
- 보조 키워드는 본문과 H3 소제목에 분산 배치한다
- 키워드 밀도보다 **자연스러운 문맥 내 사용**을 우선한다

### 산출물

6가지 항목 + SEO 키워드를 요약 정리해 사용자에게 제시한다. 사용자 확인 후 Step 2로 진행한다.

## Step 2: 구조 설계 (Structure Design)

### 블로그 글 구조 패턴

글 유형에 따라 아래 구조를 기본으로 하되, 사용자의 의도에 맞게 조정한다. 모든 구조는 **H2/H3 소제목 기반**이며, TOC 자동 생성에 대응한다.

**방법론 해설:**
```
도입: 현상 관찰 + 판단 선언 (독자가 왜 읽어야 하는지)
H2: 개념 정의 — 무엇인가
H2: 단계별 설명 — Phase 1, 2, 3 또는 원칙 1, 2, 3
  H3: 각 단계의 판단 기준과 실행 방식
H2: 주의사항 또는 오해 교정
마무리: 핵심 기준 압축 + 관점 재정렬
```

**도구·기능 리뷰:**
```
도입: 이 도구를 왜 검토했는가 (문제 상황)
H2: 핵심 기능과 평가 기준
  H3: 기능별 실험 결과
H2: 기존 도구와의 차이
H2: 어떤 상황에서 선택해야 하는가
마무리: 판단 기준 정리
```

**인사이트·관점:**
```
도입: 현상 관찰 + "그러나 본질은 다르다" 식의 반론
H2: 기존 관점의 한계
H2: 기준을 재정의하면 보이는 것
H2: 실제 적용 또는 사례
마무리: 관점 전환 — 독자가 가져갈 기준
```

**경험 기반 글:**
```
도입: 구체적 상황 제시 (강의 현장, 집필 과정, 컨설팅 장면)
H2: 그 경험에서 발견한 것
H2: 기준이 바뀐 지점
마무리: 독자에게 남기는 판단 기준
```

**가이드·튜토리얼:**
```
도입: 이 가이드가 필요한 구체적 상황
H2: 사전 준비 / 전제 조건
H2: 단계별 실행
  H3: 각 단계 (프롬프트 예시, 스크린샷 위치 표시 포함)
H2: 자주 발생하는 문제와 대응
마무리: 핵심 실행 기준 정리
```

### 소제목(H2/H3) 설계 규칙

소제목은 TOC에 표시되므로, **독자가 소제목만 읽어도 글의 골격을 파악**할 수 있어야 한다.

- H2는 2~5개. 글의 핵심 블록을 나눈다
- H3는 H2 안에서 세부 항목을 나눌 때 사용한다. H2당 0~3개
- 소제목은 **판단·행동 중심 문장** 또는 **개념 정의형**으로 작성한다
- 기능명이나 명사 나열 금지 (예: ✕ "프롬프트 종류" → ○ "초안 프롬프트와 수정 프롬프트는 분리되어야 합니다")

**소제목 유형:**

| 유형 | 예시 | 적합한 상황 |
|------|------|------------|
| 판단 선언형 | "AI의 강점은 실행, 인간의 역할은 결정" | 핵심 주장을 소제목으로 |
| 질문형 | "NotebookLM 기반 리서치 글쓰기가 필요한 이유" | 독자의 궁금증 유도 |
| 단계형 | "Phase 1. 인간 – 전략적 설계 (20%)" | 방법론·프로세스 해설 |
| 번호+개념형 | "① What → Why → How" | 구조 비교·분류 |

### 제목 설계

sshong.com 블로그 제목은 **검색 결과에서 클릭을 결정**하는 첫 번째 요소다. 아래 규칙을 적용한다.

**제목 규칙:**
- SEO 핵심 키워드를 자연스럽게 포함한다
- **핵심 판단이 제목 안에 드러나야 한다** — 정보성 제목보다 관점 제시형 제목
- 시리즈 글은 앞에 번호를 붙인다: ①, ②, ⓪ 등
- 50자 이내 권장 (검색 결과에서 잘리지 않는 범위)

**제목 유형:**

| 유형 | 예시 | 적합한 글 |
|------|------|----------|
| 주장형 | "AI 글쓰기의 핵심은 생성이 아니라 수정 설계이다" | 관점·인사이트 중심 |
| 질문형 | "좋은 글은 어떻게 작성하는가?" | 독자의 검색 의도와 일치하는 글 |
| 선언형 | "AI를 잘 쓰는 시대는 끝났다, 이제는 버는 단계다" | 트렌드·변화 분석 |
| 기준 제시형 | "AI 이미지 수정의 3가지 설계 원칙" | 방법론·가이드 |
| 도구+결과형 | "챗GPT, 책 초안 정리 및 확장 전략 프롬프트 5종 세트" | 도구 리뷰·가이드 |

제목 후보를 **5개** 생성한다.

### 내부 링크 계획

글 내에 삽입할 내부 링크를 미리 파악한다.
- 동일 카테고리의 관련 글 2~3개
- 시리즈 글이면 이전/다음 글
- 참조가 필요한 기존 가이드 글

### 산출물

아웃라인(H2/H3 소제목 포함) + 제목 후보 5개 + 내부 링크 후보 + SEO 키워드 배치 계획을 사용자에게 제시한다. 사용자 확인 후 Step 3으로 진행한다.

## Step 3: 초안 작성 (First Draft)

### 초안 작성 규칙

- Step 2에서 확정된 구조(H2/H3)를 따라 작성한다
- 공통 집필 원칙(서술 전략, 문체 기준, 금지어 규칙)을 적용한다
- **도입부 3~4문장에 특별히 집중한다** — 검색 결과의 메타설명과 글 첫 화면에 노출되는 구간
- 분량: 공백 포함 **1,200~2,500자** (3~7분 읽기 기준)
- 문단은 2~5문장 이내 유지. 문장별 독립 줄바꿈(모바일식 배치)은 사용하지 않는다
- 소제목(H2)은 마크다운 `##`로, 하위 소제목(H3)은 `###`로 표기한다
- 이미지 삽입 위치 표시: `[IMAGE: 설명]` — 글과 직접 관련된 이미지만
- 내부 링크 삽입 위치 표시: `[LINK: 관련글 제목]` — Step 2에서 계획한 링크

### 도입부 설계

검색 유입 독자는 **첫 3~4문장에서 이 글이 자신의 문제를 다루는지 판단**한다. 다음 중 하나의 방식으로 시작한다.

| 방식 | 예시 | 효과 |
|------|------|------|
| 현상→판단 | "AI로 글을 쓰는 사람은 늘어났습니다. 그러나 결과물의 완성도는 여전히 크게 갈립니다." | 독자의 경험과 접점, 판단 기대 |
| 질문→통념→반론 | "어떤 글이 좋은 글일까. 누군가는 화려한 문장을 답으로 내놓지만, 본질은 다르다." | 사고 자극, 반전 |
| 선언→설명 | "'AI 수정은 이제, 당연한 작업의 일부입니다.' AI가 만들어주는 결과물은 완성본이 아니라…" | 명확한 관점 제시 |
| 상황 제시 | "세 번째 수정 요청을 받았을 때, 문제는 글이 아니었다." | 경험 공감 |

**금지되는 도입:**
- "오늘은 ~에 대해 이야기하겠습니다"
- "~란 무엇인가? ~는 ~를 의미한다" (사전식 정의로 시작)
- "최근 ~가 화제입니다" (뉴스 리드식)

### 결론 설계

블로그 글의 결론은 요약이 아니라 **핵심 메시지 압축 + 독자의 다음 판단 기준**이다.

- 3~5문장 이내
- 본론의 내용을 반복하지 않는다
- 독자가 이 글을 읽고 무엇을 기준으로 판단하면 되는지를 명확히 한다
- 관련 글로의 연결이 자연스러우면 마지막에 내부 링크를 배치한다

### 산출물

- 초안은 **대화창 텍스트로 직접 제공**한다 (파일 생성하지 않음)
- 사용자가 파일을 명시적으로 요청한 경우에만 `draft.md`로 저장한다
- 사용자 확인 후 Step 4로 진행한다

## Step 4: 리라이팅 (Rewriting)

> **리라이팅 원본 보존 원칙** (`writing-principles.md` 참조): 리라이팅은 내용을 바꾸지 않는다. 같은 내용을 더 정확하고 읽기 좋은 문장으로 다듬는다. 구조 변경이 필요하면 별도 제안으로 분리한다.

### 역할 전환 선언 (리라이팅 진입 조건)

이 단계에서는 초안 작성자의 시점을 내려놓는다. 편집자로서, 작성 의도를 참고하지 않고 **독자 시점에서만 판단**한다. "왜 이렇게 썼는가"가 아니라 "독자가 읽었을 때 작동하는가"를 기준으로 점검한다. 이 선언 없이 체크리스트를 돌리면, 구조적 문제보다 표현만 다듬는 쪽으로 흐른다.

초안을 5가지 관점에서 점검하고 수정한다.

### 진행 방식

1. **점검 리포트 제시** — 5가지 점검 결과를 표 형태로 사용자에게 보여준다
2. **사용자 확인** — 수정 방향에 대해 동의 또는 추가 지시를 받는다
3. **수정본 작성** — 확인된 방향에 따라 전체 수정본을 제시한다
4. **변경 요약** — 수정본 하단에 주요 변경 사항을 간결하게 정리한다

사용자가 "리라이팅해줘"라고만 요청한 경우, 1~4를 한 번에 진행한다.

### 점검 1: 도입부 점검

| # | 점검 항목 | 수정 방향 |
|---|----------|----------|
| 1 | 첫 문장이 현상 관찰·질문·선언·상황 제시 중 하나로 시작하는가 | 정의·나열·메타 서술로 시작했다면 교체 |
| 2 | 첫 3~4문장 안에 독자가 계속 읽을 이유가 있는가 | 검색 의도와의 접점이 작동하는지 확인 |
| 3 | 메타설명으로 활용 가능한가 | 첫 2문장이 검색 결과 미리보기에서 매력적인지 점검 |

### 점검 2: 구조 점검

| # | 점검 항목 | 수정 방향 |
|---|----------|----------|
| 1 | H2/H3 소제목만 읽어도 글의 골격이 파악되는가 | 모호한 소제목 재작성 |
| 2 | 전체 흐름이 상황 → 기준 → 적용 순서를 따르는가 | 순서 재배치 |
| 3 | TOC에 표시될 때 구조가 명확한가 | 소제목 레벨(H2/H3) 조정 |
| 4 | 마무리가 핵심 메시지 압축 + 판단 기준 제시로 끝나는가 | 요약형·감상형 마무리를 기준 제시형으로 전환 |

### 점검 3: 문장·금지어 점검

| # | 점검 항목 | 수정 방향 |
|---|----------|----------|
| 1 | "~할 수 있습니다"가 있는가 | 단정형 전환 |
| 2 | "매우, 쉽게, 빠르게"가 있는가 | 수치·조건·단계로 대체 |
| 3 | 과장형 형용사가 근거 없이 쓰였는가 | 비교 기준 또는 수치로 교체 |
| 4 | 추상 명사가 문장 중심에 있는가 | 동사 중심 문장으로 전환 |
| 5 | 문장이 15~25단어 범위 내인가 | 초과 시 분리 |
| 6 | AI 흔적 조합(부사+형용사+가능성+추상명사)이 있는가 | 해체 후 재구성 |

### 점검 4: 스타일 점검

| # | 점검 항목 | 수정 방향 |
|---|----------|----------|
| 1 | 방법·팁이 기준 설명 없이 먼저 등장하지 않는가 | 기준 문단 추가 |
| 2 | 단락이 일반 문서 형식(2~5문장 단위)으로 작성되었는가 | 문장별 독립 줄바꿈 있으면 단락으로 통합 |
| 3 | 문체 리듬이 점층 구조를 따르는가 | 관찰 → 판단 순서로 조정 |
| 4 | 종결어미가 일관적인가 | '~습니다'체 또는 '~다'체 통일 |

### 점검 5: 블로그 최적화 점검

| # | 점검 항목 | 수정 방향 |
|---|----------|----------|
| 1 | 분량이 1,200~2,500자 범위 내인가 | ±20% 이내로 조정 |
| 2 | SEO 핵심 키워드가 제목과 H2에 자연스럽게 포함되었는가 | 부자연스러운 삽입은 제거, 누락 시 추가 |
| 3 | 내부 링크가 적절한 위치에 배치되었는가 | 문맥과 무관한 링크 제거, 필요한 링크 추가 |
| 4 | 이미지 위치가 글의 흐름과 맞는가 | `[IMAGE]` 마커 점검 |
| 5 | 제목이 검색 결과에서 매력적이며 50자 이내인가 | 제목 재설계 |

### 변경 요약 표준 포맷

## Step 5: 발행 준비 (Publish Ready)

Step 4 수정본을 워드프레스 발행 수준으로 마무리한다.

### 진행 방식

1. **최종 점검 실행** — 아래 항목을 점검하고 결과를 사용자에게 제시한다
2. **제목 확정** — 후보를 제시하고 사용자가 선택한다
3. **발행 메타 정보 작성** — 카테고리, 태그, 메타설명, 대표 이미지 방향
4. **사용자 확인** — 최종본을 보여주고 확정 여부를 확인한다
5. **파일 생성** — 확정 후 파일을 생성한다

### 최종 점검 항목

| # | 점검 항목 | 기준 |
|---|----------|------|
| 1 | 제목 확정 | 후보 5개 중 선택 또는 새로 생성. SEO 키워드 포함, 50자 이내 |
| 2 | 맞춤법·문법 교정 | 한국어 맞춤법, 띄어쓰기, 외래어 표기법, 문장부호 |
| 3 | 카테고리 선택 | sshong.com 카테고리 중 1~2개 지정 |
| 4 | 태그 선정 | 2~4개. 기존 태그와의 일관성 유지 |
| 5 | 메타설명 작성 | 150자 이내. 검색 결과에 표시될 요약문. 핵심 키워드 포함 |

### 시리즈 연계 안내

- 시리즈 글이면 이전/다음 글과의 연결을 확인한다
- 시리즈 번호(①②③)가 제목에 포함되었는지 확인한다
- 시리즈 색인 글(⓪)이 있다면 해당 글에 새 글 링크 추가를 안내한다

## 분량 통제 규칙

### 원문 보존 강도 레벨

사용자의 요청 동사에 따라 보존 강도를 자동 판별한다. 레벨을 혼동하지 않는다.

| 레벨 | 트리거 | 허용 범위 | 금지 행위 |
|------|--------|----------|----------|
| **L1 교정** | "다듬어줘", "교정해줘", "수정해줘" | 맞춤법·띄어쓰기·종결어미 통일만. 문장 구조 변경 금지 | 문장 분리·병합, 새 문장 추가, 문단 재배치 |
| **L2 정리** | "정리해줘", "깔끔하게", "보강해줘" | 문장 분리·접속 보강, 지정 부분 내용 추가. 미지정 부분 원본 유지 | 구조 재배치, 슬롯 순서 변경, 미지정 부분 수정 |
| **L3 리라이팅** | "리라이팅해줘", "다시 써줘" | 구조 재배치·문장 교체·패턴 적용 허용 | 분량 120% 초과 (초과 시 사유 확인) |

- 사용자가 레벨을 명시하지 않으면 트리거 동사로 자동 판별한다
- 수정 결과물이 2,500자를 초과하면, 초과 사유를 사용자에게 먼저 확인한다
